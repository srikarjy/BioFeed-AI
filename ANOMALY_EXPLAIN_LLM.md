# Anomaly Explanations via Self-Hosted vLLM

Backend-only feature: when the anomaly pipeline flags a candidate
early-signal event, `GET /internal/anomaly-explain/{event_id}` streams a
short natural-language explanation generated by a self-hosted quantized LLM
served with vLLM, instead of calling a hosted API.

No iOS/SwiftUI changes. Nothing here touches the existing public
articles/search/ingestion routes or the anomaly detector's scoring logic —
everything added is additive and lives in `backend/app/anomaly/`,
`backend/app/llm/`, `llm_serving/`, `scripts/`, and `observability/`.

## What exists today, honestly

- **Anomaly pipeline**: this repo had no anomaly detection before this
  change. `backend/app/anomaly/` adds a minimal, real one — a cross-source
  burst detector (`detector.py`) that reuses the existing pgvector
  embeddings and `crud.find_similar` to flag an article when other sources
  publish closely matching coverage within a 48h window. It's intentionally
  simple; it exists so the LLM-explanation feature has a real event to
  consume instead of a mocked schema. See `backend/app/anomaly/detector.py`
  for the exact heuristic and thresholds.
- **LLM route**: real, tested against a local stand-in server.
- **vLLM serving scripts**: real, but **not yet run against a real GPU** —
  no rented GPU instance was available while building this. Scripts are
  written and documented below; treat them as unverified until you run them.
- **Benchmark numbers in `benchmarks/report.md`**: real numbers, but from a
  local CPU stand-in (`scripts/stub_vllm_server.py`), not from vLLM or a
  GPU. They validate the wiring (FastAPI route → SSE → client), not serving
  performance. See the caveats in that file before quoting them anywhere.
- **Grafana dashboard**: panel queries use vLLM's actual native Prometheus
  metric names (`vllm:num_requests_running`, `vllm:gpu_cache_usage_perc`,
  `vllm:time_to_first_token_seconds`, etc.) but have not been screenshotted
  against a live vLLM server, since none was running. Raw GPU compute
  utilization (SM%, memory bandwidth) is **not** part of vLLM's native
  `/metrics` — that requires a separate exporter (e.g. `dcgm-exporter` or
  `nvidia_smi_exporter`) which is not included here; only `gpu_cache_usage_perc`
  (KV cache occupancy) comes from vLLM itself.

## Layout

```
backend/app/anomaly/     AnomalyEvent model, cross-source burst detector, internal routes
backend/app/llm/         vLLM client, prompt builder, SSE route (isolated, LLM_ENABLED to disable)
llm_serving/              GPU-instance deployment scripts (vLLM OpenAI-compatible server)
scripts/
  stub_vllm_server.py     local CPU stand-in OpenAI-compatible server, for wiring validation only
  bench_anomaly_explain.py  async load-testing tool, run against a real running server
observability/            docker-compose Prometheus + Grafana, scrapes a remote vLLM /metrics
benchmarks/                report.md + per-run JSON from load-testing runs
```

## 1. Spin up the GPU instance and start vLLM

On a rented A10G/L4-class instance (image with NVIDIA driver + CUDA
preinstalled — Lambda, RunPod, vast.ai all offer these):

```bash
scp -r llm_serving/ user@gpu-host:~/llm_serving
ssh user@gpu-host
cd llm_serving
cp .env.example .env   # edit VLLM_MODEL/PORT/etc. if needed
./startup.sh           # venv + pip install + model download + serve.sh
```

`startup.sh` chains `download_model.sh` (pulls the AWQ checkpoint into the HF
cache) and `serve.sh` (launches
`python -m vllm.entrypoints.openai.api_server` with the documented engine
args — see comments in `serve.sh` for what each flag does and why).
Continuous batching (PagedAttention scheduling) is vLLM's default behavior;
no flag turns it on, `--max-num-seqs` only bounds how wide it gets.

Confirm it's up:
```bash
curl http://<gpu-host>:8000/v1/models
curl http://<gpu-host>:8000/metrics | head
```

## 2. Point the backend at it

In `backend/.env` (or exported env vars):
```
LLM_ENABLED=true
LLM_VLLM_BASE_URL=http://<gpu-host>:8000/v1
LLM_VLLM_MODEL=TheBloke/Mistral-7B-Instruct-v0.2-AWQ
```

These are read by `backend/app/llm/config.py`, isolated from the main
`app/config.py` `Settings` so this whole feature can be deleted without
touching it.

## 3. Seed an anomaly event and call the route

```bash
curl -X POST http://localhost:8000/ingest/run
curl -X POST http://localhost:8000/internal/anomaly/detect
curl http://localhost:8000/internal/anomaly/events?limit=1   # note an id

curl -N http://localhost:8000/internal/anomaly-explain/<event_id>
```

`-N` disables curl's output buffering so you see the SSE `data:` lines
arrive incrementally.

## 4. Run the benchmark

Without a GPU, validate wiring locally first:
```bash
python -m uvicorn scripts.stub_vllm_server:app --port 9100 --app-dir .
# in another terminal, with the backend pointed at LLM_VLLM_BASE_URL=http://localhost:9100/v1
# and a real running backend server + seeded event id:
python scripts/bench_anomaly_explain.py --base-url http://localhost:8000 \
  --event-id <id> --concurrency 10 --requests 50 --label stub-cpu
```

Against real vLLM on GPU, same command with `LLM_VLLM_BASE_URL` pointed at
the GPU host and `--label vllm-a10g`. Results append to `benchmarks/report.md`
and land as JSON under `benchmarks/`.

The numbers currently in `benchmarks/report.md` were produced a different
way (in-process ASGI transport, no live backend/Postgres available in this
environment) — see that file's "How this was produced" section for the
exact method and a known TTFT-measurement artifact of that approach.

## 5. View the dashboard

```bash
cd observability
# edit prometheus.yml: replace YOUR_GPU_HOST:8000 with the real host:port
docker compose up -d
open http://localhost:3000   # Grafana, anonymous viewer access enabled
```

The "vLLM - Anomaly Explanation Serving" dashboard is auto-provisioned
(`observability/grafana/dashboards/vllm-anomaly-explain.json`) — no manual
import needed. This stack runs locally/separately from the GPU box; it only
scrapes `http://<gpu-host>:8000/metrics` over the network, never runs
anything on the GPU instance itself.

## Removing this feature

Everything is isolated:
- Delete `backend/app/llm/` and remove its two lines in `backend/app/main.py`.
- Delete `backend/app/anomaly/` (and its two lines in `main.py`/`alembic/env.py`),
  plus drop the `anomaly_events` table via the `0004` migration's `downgrade()`.
- Delete `llm_serving/`, `scripts/stub_vllm_server.py`,
  `scripts/bench_anomaly_explain.py`, `observability/`, `benchmarks/`.

Or just set `LLM_ENABLED=false` to disable the route without removing code.
